# 低代码数据对齐计划（YAAI 前台消费）

> 目标：使 **`yaai-lowcode` 产出的菜单、页面、版本、节点树、组件定义、数据绑定、片段** 能被成员 4 **YAAI** 按契约稳定消费。  
> 依据：[前台接入后台低代码说明.md](./前台接入后台低代码说明.md)、[接口字段差异记录.md](../01_设计基线/接口字段差异记录.md)、`YAAI` 只读扫描结果、低代码类型定义（`src/types/*`，本文仅引用语义不写代码）。

---

## 0. `component_key` 正式白名单（已冻结）

**唯一权威**：[component_key白名单.md](../01_设计基线/component_key白名单.md)。

- 新配置的节点**仅允许**使用该文件中的 10 个业务键 + 根容器 `page_container`。  
- **`service_matrix` / `event_list` 不再作为可选名**：视为**历史别名**，新数据统一为 **`home_services`**、**`home_events`**。  
- 成员 4 的 **`component-map.ts`** 以白名单为准；未知键渲染 **`UnknownComponent`**，不得崩溃。  
- 存量库中若仍存在别名或旧键，纳入 **数据清洗 / 节点迁移**（见 `数据库清洗候选清单.md`），不在此文件保留「二选一」。

## 1. `menu` 对齐计划

### 1.1 现状与目标

- **类型语义**（低代码）：`Menu` 含 `parent_id`、`name`、`code`、`url_type`（`page` | `external`）、`page_id`、`external_url`、`sort_order`、`status`（见 `src/types/menu.ts`）。  
- **YAAI 顶栏**：首页 `/`、关于（多子链）、`/services`、`/news` 与动态 `/news/c/:id`、`/conference`。  
- **对齐原则**：后台菜单树的 **「可点击目标」** 必须能落到 YAAI **已存在** 的 `path`，或外部 `https://` 外链；避免出现后台 `page.path` 在前台路由器中未注册。

### 1.2 树形与排序

- 使用与低代码一致的 **`buildMenuTree`** 规则：`parent_id` + `sort_order`（与 [接口字段差异记录.md](../01_设计基线/接口字段差异记录.md)、编辑器 store 描述一致）。  
- **一级菜单** 建议与 Navbar 五大区块对齐；**关于我们**、**新闻分类** 等二级项对应子路由。

### 1.3 `url_type` 与解析

| `url_type` | 行为 | YAAI 侧 |
|------------|------|---------|
| `page` | 解析 `page_id` → 关联 `page.path` → `router.push(path)` | 需保证 `path` 唯一且已注册 |
| `external` | `window.open(external_url)` 或 `<a>` | 与顶栏「外链菜单」一致 |

### 1.4 与「新闻分类」并存

- YAAI 新闻下拉与侧栏来自 **`/news-categories`** 类接口，不是 `menu` 表唯一来源。  
- **对齐策略（推荐）**：  
  - **频道级**（指向 `/news` 或某一 `categoryId`）可由 `menu` 指向固定 `page.path`（如 `/news`），分类细化仍走新闻分类 API；  
  - 或在后续产品中约定「菜单项绑定 categoryId」——需**后端契约扩展**，本轮仅记为可选方向。

## 2. `page` / `path` 对齐计划

### 2.1 `page` 核心字段

- **`path`**：必须与 YAAI 路由一致（见 `前台结构映射分析.md`）。优先列表：  
  - `/`、`/services`、`/conference`（及若启用的子路径）  
  - `/about/introduction` … `/about/local`  
  - `/news`、`/news/c/{id}`（{id} 为具体数字 —— 一般由分类驱动，静态 page 可存模板路径或不使用动态页）  
  - `/content/{id}` 一般不作为「栏目页」path，而是详情页由列表跳转产生；低代码若做「栏目首页」，仍建议 `/news` 或 `/news/c/x`。

### 2.2 `page_type` / `code` / `title`

- **`code`**：建议稳定英文蛇形或业务缩写（如 `home`、`about_intro`），便于成员 4 做埋点与缓存键。  
- **`page_type`**：与后端枚举对齐；门户首页可标记为 `portal`，栏目页 `channel`，纯静态 `static` 等（以数据库设计 v6 为准）。

### 2.3 首页 / 新闻 / 通知 / 关于 / 服务 / 会议 — `path` 设计建议

| 业务 | 建议 `page.path` | 备注 |
|------|------------------|------|
| 首页 | `/` | 单页 |
| 服务矩阵 | `/services` |  |
| 会议 | `/conference` | 子 tab 若仍同组件，可用同一 path 或后续前台增加 query |
| 关于子页 | `/about/introduction` 等六个固定 path | 与 `sidebarGroups.about` 一致 |
| 新闻聚合 | `/news` | 分类列表用 `/news/c/{categoryId}` |
| 「通知」 | YAAI 首页为 `HomeNotice`，独立通知列表若暂无路由——**需前台新增路由** 或并入 `/news` 某分类 | 见对齐风险 |

## 3. `page_version` / `current_version_id` 对齐计划

### 3.1 语义

- **`page_version`**：`status` 含 `draft` / `published` / `archived`（类型见 `src/types/page-version.ts`）。  
- **`page.current_version_id`**：应指向 **当前对外发布版本** 的 `page_version.id`（与 `PublishPageVersionResponse` 语义一致）。

### 3.2 如何保证「有效」

1. **发布闭环**：仅当 **`published`** 成功写入且后端返回更新后的 `page.current_version_id` 后，前台才应展示新版本（成员 4 读取以服务端为准）。  
2. **禁止悬空的 `current_version_id`**：删除 / 归档版本前，需先切换或回滚 `page` 指向；建议在运营流程中 **先发布再删旧**。  
3. **联调校验**：比对 `GET /pages/{id}` 与 `GET /pages/{pageId}/versions` 中 `published` 条目是否一致。

## 4. `page_node` 节点树对齐计划

### 4.1 与低代码编辑器一致的消费规则（成员 4 侧）

参考 `src/utils/tree.ts`：

- 输入：平铺 `PageNode[]`  
- 建树：`parent_id == null` 为根；父子通过 `parent_id` 链接；同父节点按 **`sort_order`** 排序。  
- **槽位**：`slot_name` 用于区分子节点插入位置；文档与 `NodeRenderer` 提及 **`main` / `left` / `right`** 等。

### 4.2 树形设计建议（让前台「能渲染」）

1. **单根或多根**：常态 **单根** `container`（`component_key: page_container`），`slot_name: main`，与 mock `701` 节点一致。  
2. **子节点顺序**：纵向首页区块按下拉顺序设 `sort_order`。  
3. **`node_type`**：`container` 套区块；叶子为 `component`；跨页复用 `fragment_ref`（仅当成员 4 实现片段展开或后端返展开树）。  
4. **`component_key`**：必须在 [component_key白名单.md](../01_设计基线/component_key白名单.md) 内，且对应 `component_def` 存在并 `status: true`。**禁止**再新增「服务矩阵 / 活动」的第二套正式键名。

### 4.3 与当前 YAAI `NodeRenderer`（后台编辑器内）的关系

- `yaai-lowcode` 内 `NodeRenderer.vue` 用于 **管理端预览**，**不是** YAAI 运行时组件。  
- **对齐目标**：键名、props 约定一致，成员 4 实现自己的 `PublicNodeRenderer` 时复制「解析 JSON + 映射组件」模式即可。

## 5. `component_def` 对齐计划

1. **每个白名单 `component_key`** 在 `component_def` 中有且仅有一条主记录（或明确的多环境策略），并含 `prop_schema_json` / `default_props_json` 等说明。  
2. **容器**：仅 `page_container` 作为页面根容器（`is_container: true`）；子区块使用白名单中的叶子组件键。  
3. **可绑定数据**：`can_bind_data: true` 时，`data_binding` 的 `binding_type` / `source_key` 与 CMS 接口可映射（示例见 `src/mock/database.ts`）。  
4. **与 YAAI 首页对齐**：白名单已固定 **`home_services`、`home_events`、`friend_links`** 等键名；若库中仍为旧名，按 [数据库清洗候选清单.md](../05_数据库清洗/数据库清洗候选清单.md) 做改名或停用。

---

## 6. `data_binding` 对齐计划

| 维度 | 计划 |
|------|------|
| `binding_type` | 与 CMS 接口语义对齐：`banner_group`、`article_category`、`site_config` 等（示例见 mock） |
| `source_key` | 稳定字符串（如 `home_banner`、`notice`），与后端查询参数约定一致 |
| `query_json` | 分页、条数、`categoryId` 等；成员 4 消费时转为真实请求参数 |
| `field_map_json` | 将后端字段映射为前台组件 props（如 `image` ← `image_url`） |

**接口输出保证**：后台保存的 `data_binding` 应能在 **展示端只读接口** 上「预览或执行查询」——具体只读路径以 [前端需求接口文档_v2.0.md](../01_设计基线/前端需求接口文档_v2.0.md) 与后端实现为准。

## 7. `reusable_fragment` 对齐计划

- 用于 **跨页重复**（页脚、备案信息、二维码条等）。  
- YAAI 当前 Footer 为手写组件；若走上配置化，可由 **`fragment_ref`** 节点引用。  
- **风险**：成员 4 若未实现 `fragment_ref` 展开，需后端 **flatten** 或暂缓使用片段。

---

## 8. 对成员 4 的接口输出保证（责任边界）

成员 3/后端需保证（与 [前台接入后台低代码说明.md](./前台接入后台低代码说明.md) 一致）：

1. **菜单**：完整层级、禁用项 `status: false` 过滤规则明确。  
2. **页面**：`path` 唯一；`current_version_id` 可解析。  
3. **版本树**：`GET /page-versions/{id}/node-tree` 返回 **平铺 nodes**，JSON 字段为字符串或 null；`componentKey` 可空情况有业务说明。  
4. **发布**：发布后 `page` 与 `page_version` 状态一致；避免「成功但 parentId 丢失」类后端问题（见 `接口字段差异记录` 整树 PUT 章节）。  
5. **camelCase / records**：以 `接口字段差异记录` 为准做适配，不强制前端重复造字段。

## 9. 协作问答 5～9 的简要结论

5. **`page.path`**：与 YAAI Router 已注册路径严格一致；动态分类用 `/news/c/:id` 时 id 来自分类数据。  
6. **`menu` 清洗成官网导航**：以 Navbar 五区为骨架，`page` 链或外链填充；新闻细类与分类 API 协同。  
7. **`current_version_id`**：仅指向 **已发布** `page_version`；通过发布接口原子更新；删除版本前先切换。  
8. **`page_node` 树**：单根容器 + 顺序区块 + 合法 `slot_name` / `sort_order`；绑定数据用 `data_binding_id`。  
9. **`props_json`**：与 YAAI 各区块 props 对齐（标题、条数、`showDate`、`columns`、富文本 `html` 等），并沿用 mock 中已验证的键名作为起点。
