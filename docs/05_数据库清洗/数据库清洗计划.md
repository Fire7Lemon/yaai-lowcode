## 1. 清洗目标

1. **菜单 `menu`**：与真实官网信息架构一致，可支撑顶栏与侧栏（在契约允许范围内）。  
2. **页面 `page` + `path`**：与 YAAI 路由一一对应或可解释的唯一映射，无幽灵 path。  
3. **版本 `page_version`**：`published` 与 `page.current_version_id` 同步；清理无归属草稿、失效联调用版本。  
4. **节点 `page_node`**：`component_key` 均可映射到目标 `component_def`；减少 `component_key`/绑定为空的脏节点（与 `接口字段差异记录` 观测一致）。  
5. **`data_binding` / `component_def`**：去掉演示用途、测试域名、无后端来源的绑定。  
6. **可重复执行**：清洗分阶段，**先备份、再删改、再验证、可回滚**。

## 3. 需要保留的数据

- **已与 YAAI 路由对齐且正展示** 的 `page` / `published` `page_version` / 其 `page_node` 树。  
- **被 `menu` 引用** 的 `page_id`（除非同步调整菜单）。  
- **`component_def` 正在被节点引用** 的记录（即使命名不完美，也应先「迁移节点 → 再下线定义」）。  
- **prod 环境种子数据** 中业务已依赖的 `data_binding`（如正式 banner、notice 源）。

## 4. 需要人工确认的数据（禁止脚本直接删）

1. **`menu` 指向 `page_id` 但 path 与 YAAI 不一致** —— 需产品决定改菜单还是改 `page.path`。  
2. **`current_version_id` 指向已删除 / 草稿版本** —— 需确认应回滚到哪一版 `published`。  
3. **整树 PUT / copy 产生的异常 `parent_id`（文档记载副本问题）** —— 需后台修复或手工修树前留存证据。  
4. **与新闻分类 ID 绑定的页面** —— 分类数据以运行时 API 为准，删页面前确认分类仍存在。  
5. **多环境共用库** —— 确认当前连接的是联调库还是预发 / 生产。

## 5. 建议新增的真实页面（数据层「应有」）

结合 `前台结构映射分析.md` 与 YAAI 路由：

| 建议 `page.path` | 用途 |
|------------------|------|
| `/` | 首页 |
| `/services` | 服务矩阵 |
| `/conference` | 会议系统入口 |
| `/about/introduction` … `/about/local` | 关于子页（6 页，可分步） |
| `/news` | 新闻入口（与分类联动） |

*若某 path 在 YAAI 仍为静态实现，数据库仍建议有占位 `page`，便于菜单 `url_type=page` 统一。*

## 6. 建议新增的真实菜单（骨架）

与 Navbar 对齐的一级项（名称可按品牌微调）：

1. 首页 → `page` `/`  
2. 关于云智会 → 父级 + 子级指向各 `/about/*`  
3. 服务矩阵 → `/services`  
4. 新闻动态 → `/news`（子项可部分来自 `news-categories`，与 menu 表协同方案见对齐计划）  
5. 会议系统 → `/conference`  
6. （可选）外部合作 / 外链 → `url_type: external`  

**删除/替换** mock 中的「外部站点 example.com」类项，除非品牌确有该外链。

## 8. 建议新增的首页 node-tree（逻辑结构）

参考 mock `pageNodes` 中 `version 101` 结构，扩展为贴近 YAAI 首页顺序：

1. 根：`page_container`，`slot_name: main`  
2. 子节点 1：`hero_banner` + `data_binding_id`（banner）  
3. 可选：`hero_split_container` 下 **左 `notice_list` 右 `quick_links`**（与 YAAI 当前两列布局一致）  
4. 依次：`home_services`、`home_events`、`news_list`、`home_shortcuts`、`friend_links`  

**注意**：若需两列（通知 + 快捷入口），可用 **槽位** `left` / `right` 或与编辑器约定的布局容器；**业务 `component_key` 仍以白名单为准**。

## 9. 下一轮「生成数据库清洗 SQL」建议步骤（仍非本文执行）

1. **全库备份**（逻辑备份 + 文件快照）。  
2. **导出版本清单**：`page` / `page_version` / `page_node` 计数与孤儿检测查询（只读分析脚本）。  
3. **标记候选行**：按 §2 关键词筛选，导出 CSV **人工签字**。  
4. **冻结写入**：清洗窗口停止后台编辑器发布。  
5. **按依赖顺序删除或更新**：  
   - 先解绑 `menu.page_id`  
   - 再归档或删除 `page_node` → `page_version` → `page`  
   - 最后清理 `data_binding`、`component_def`（确认无引用）  
6. **插入/更新** 真实菜单、页面、发布版本、节点树（通过后台 API 优先，裸 SQL 为辅）。  
7. **验证**：抽样 `GET` 菜单、按 path 拉 page、拉 `node-tree`；对照 YAAI 手点路径。  
8. **回滚**：恢复备份或执行逆向脚本。

## 10. 风险与回滚建议

| 风险 | 缓解 |
|------|------|
| 删错 `page_version` 导致链路断开 | 先设 `current_version_id` 到新版本，再删旧版 |
| 整树写入 snake_case 导致结构损坏 | 后台 API 层已要求 camelCase；清洗后只用官方 API 或已验证脚本 |
| 与成员 4 键名不一致 | 清洗前锁定 `component_key` 清单 |
| 生产误操作 | 双人复核 + 备份 + 限量分批 |
