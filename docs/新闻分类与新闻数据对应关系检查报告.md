## 4. 字段关系说明（核心，代码可证）

### 4.1 后端数据模型（v6.0）

- **`news_category.parentId`** → 指向 **`news_category.id`**（新闻分类自关联；顶级分类 `parentId=null`）。与菜单无关。
- **`news.categoryId`** → 指向 **`news_category.id`**（外键 `fk_news_category`）。即「新闻属于哪个新闻分类」。
- **`menu.parentId`** → 指向 **`menu.id`**（菜单自关联）。**与 `news_category.parentId` 完全无关**，是两套独立的层级。
- **`data_binding.sourceKey`** → 业务约定的「数据源标识」。本库 id=1 的 sourceKey=`news_category_xhxw`，按命名约定**对应新闻分类的 `code`（= `news_category_xhxw`）**，**不是** `news_category.id`、**不是** menu id。

### 4.2 YAAI 展示端实际怎么过滤新闻（关键，对不上的根因）

只读 `YAAI/src/api/news.ts` + `YAAI/src/composables/useNewsListByCategoryId.ts`：

```37:55:YAAI/src/api/news.ts
/**
 * 展示端新闻列表 `GET /news/show-list`
 * @param category_id 与菜单项 `id` 一致，对应新闻 `categoryId`
 */
export function fetchNewsShowList(params: { category_id?: number; ... })
```

```16:18:YAAI/src/composables/useNewsListByCategoryId.ts
/**
 * 按菜单 id 展示新闻列表：内部 `GET /news/show-list`（`category_id` = 菜单 id）
 */
```

- YAAI `fetchNewsListByCategoryId(menuCategoryId)` 把 **菜单 id** 当作 `category_id` 传给 `GET /news/show-list`。
- 即 **YAAI 用「menu.id」过滤新闻**，并假设 `news.categoryId == menu.id`。
- 而后端 `news.categoryId` 实际指向 **`news_category.id`**。

> **结论（根因）**：当前链路里同时存在 **三种不同的标识**，互不相等：
> 1. **menu.id**（YAAI `show-list` 实际用它当 `category_id` 过滤）；
> 2. **news_category.id**（`news.categoryId` 真正引用的）；
> 3. **news_category.code / data_binding.sourceKey**（`news_category_xhxw`，data_binding 声明用它）。
>
> 三者只要不相等，就会「新闻分类与新闻列表 categoryId 对不上」。且 **YAAI 当前根本没用 data_binding**（`news.ts` 注释明确「不使用 GET /news-categories」，按 menu id 过滤），所以 `dataBindingId=1` / `sourceKey=news_category_xhxw` 在前台目前是**未被消费的语义声明**。

### 4.3 节点绑定现状

- 首页 `home_news`(308/4130) 与 `/news` `news_list`(309/4134) 都挂了 **`dataBindingId=1`（sourceKey=news_category_xhxw）**。
- 但 YAAI `HomeNews` 走 `fetchLatestNews()`（取全部新闻按 updatedAt 排序前 N 条，**不按分类**）；`/news` 列表走 `fetchNewsListByCategoryId(menu.id)`（**按 menu id**）。两者都**没有读取 `dataBindingId` / `sourceKey`**。

## 10. 清洗建议（只建议，不执行）

### A. 必须清洗（待后端 GET 确认后）
- **orphan `news.categoryId`**：若存在 `news.categoryId` 在 `news_category` 找不到，必须修正新闻归类或补分类。
- **status 不一致**：若新闻引用了 `status=false` 的分类，需停用新闻或恢复分类。
- **code 与 sourceKey 明显错位**：若不存在 `news_category.code='news_category_xhxw'`，则 data_binding id=1 的 sourceKey 指向落空，需改 sourceKey 或补分类 code。

### B. 建议清洗
- **首页/新闻页共用 data_binding id=1**：建议拆分——首页「最新全部」与新闻页「按分类」用不同绑定，避免语义混乱。
- **命名/code 语义化**：`news_category_xhxw` 可读性弱，建议统一 code 命名规范（如 `xuehui_news`）。

### C. 暂不清洗
- `parentId=null` 的一级分类（正常）。
- 当前不影响展示的历史字段。

### 候选方案

- **方案 1（前台按 categoryId 显示/筛选，后台不改 code）**：前台把过滤参数从「menu.id」改为「真实 `news_category.id`」（在菜单/页面上配 category_id 映射）。**后台数据基本不动**，成本在成员4。
- **方案 2（统一按 code/sourceKey 映射）**：前台改为按 `news_category.code`（= data_binding.sourceKey）过滤；需保证 `news_category.code` 与 `data_binding.sourceKey` 一致（可能需清洗 sourceKey 或分类 code）。语义最清晰，但前后台都要动。
- **方案 3（/news 展示全部，首页 home_news 才绑定具体分类）**：`/news` 不过滤（展示全部新闻），首页 `home_news` 若要「学会新闻」再按分类绑定。最小改动、规避 menu.id≠category.id 问题；与 YAAI 现状（首页 `fetchLatestNews` 全部、新闻页按 id）最接近，只需让新闻页也走「全部」即可先跑通。

> **倾向**：联调期先用 **方案 3** 跑通展示（不阻塞），中期按 **方案 1/2** 之一定稿过滤口径。最终选型属产品 + 成员4 决策，本报告不代决。

## 11. 给成员4的字段解释（可直接复制）

> 新闻这块「对不上」的核心，是**三种 id/标识没对齐**：
> 1. **`news.categoryId` 指向的是 `news_category.id`（新闻分类表主键）**，不是菜单 id，也不是分类 code。
> 2. 但 YAAI 现在 `fetchNewsListByCategoryId()` / `useNewsListByCategoryId()` 传给 `GET /news/show-list?category_id=` 的是**菜单 id（menu.id）**（代码注释也写了「category_id = 菜单 id」）。菜单 id 与 news_category.id 是两套独立主键，不相等就过滤不到。
> 3. 后台 `data_binding id=1` 的 `sourceKey=news_category_xhxw` 是**分类的 code（字符串）**，不是 id；而且 YAAI 目前**根本没读 data_binding/sourceKey**（首页走「最新全部」，新闻页走「按 menu.id」）。
>
> 另外：`news_category.parentId` 和 `menu.parentId` 是**两套互不相关的层级**，别把它们关联。
>
> 建议先确认两件事（等后端起来我可帮你 GET 核对）：① `news_category` 里到底有哪些 id/code（是否有 `news_category_xhxw`）；② `news.categoryId` 实际取值。然后二选一：**要么前台改成用真实 `news_category.id` 过滤（方案1）**，**要么 `/news` 先展示全部、首页再按分类（方案3）**。

## 14. parentId 绑定尝试与阻塞（2026-06-02 第十二轮）

> 成员4 方案要求 `news_category.parentId → menus.id`（声明分类归属页面）。本轮尝试将分类 1/2/3 的 parentId 改为 `nav_news` 的 **menu.id=11**。

- 实测：`PUT /news-categories/1` → **`success:false`，`code=DATA_CONFLICT`，「数据冲突」**；重试 1 次仍失败，按规则停止（未改 2/3、未试 PATCH/其它路径）。
- **根因（重要）**：v6.0 schema 中 `news_category.parentId` 是**指向 `news_category.id` 的自关联外键**（`fk_news_category_parent FOREIGN KEY (parent_id) REFERENCES news_category(id)`）。写入 `menu.id=11` 引用了不存在的 news_category 行 → 外键/数据冲突。
- **结论**：成员4 方案「`news_category.parentId → menus.id`」**与后端现有 schema 直接冲突**，前端/受控写无法绕过。需后端决策三选一：① 放开/改 `parentId` 外键语义（允许指向 menu）；② 在 `news_category` 新增独立字段（如 `owner_menu_id`）承载归属，不复用 `parentId`；③ 前端改用其它方式声明分类与页面归属（如约定全部新闻类目固定属于 `/news`，不依赖 parentId）。
- 当前 parentId 仍为 null（未变）；`news.categoryId`（1/2/3）与 show-list 过滤（2/2/1）不受影响、保持正常。

## 15. 新闻分类归属字段方案（A / B / C，2026-06-02 讨论结论）

### 15.1 字段语义说明（**当前项目联调约定，2026-06-02 定稿**）

> 当前项目为了尽快完成功能，采用功能优先方案：**复用 `news_category.parentId` 表示分类所属菜单 id**。

```text
news_category.id        ：新闻分类主键
news.categoryId         ：指向 news_category.id，用于新闻筛选
news_category.parentId  ：本项目中复用为所属菜单 id，即 menus.id（不再表示父分类）
menu.id                 ：菜单主键
menu.parentId           ：菜单树父子关系，指向 menu.id
```

**铁律（不变）**：

```text
不要把 menu.id 当作 category_id。
category_id 只能传 news_category.id。
```

### 15.2 当前已验证事实

```text
/news/show-list?category_id=1 -> 2 条
/news/show-list?category_id=2 -> 2 条
/news/show-list?category_id=3 -> 1 条
news.categoryId 与 news_category.id 对应关系正常。
```

### 15.3 冲突事实

```text
尝试 PUT /news-categories/1 parentId=11 失败。
原因：11 是 menu.id，不是 news_category.id。
后端返回 DATA_CONFLICT。
说明当前 schema 不允许 parentId 保存 menu.id。
```

### 15.4 三种方案对照（**已定稿见 §15.5**）

#### 方案 A：不改后端，`/news` 固定读取全部新闻分类（**临时降级，非当前执行**）
- `/news` 页面直接调用 `GET /news-categories`，**不按 parentId 筛选**；
- 分类 Tab 使用 `news_category.id`；`/news/show-list?category_id=` 传 `news_category.id`；
- **优点**：最快，无后端改动；
- **缺点**：只适合"当前仅 `/news` 一个页面使用新闻分类"的情况（多页面共用分类时无法区分归属）。

#### 方案 B：不新增字段，复用 `parentId = menu.id`（**当前最终采用**）
- `news_category.parentId` 复用为"所属菜单 id"；`news.categoryId` 仍指向 `news_category.id`；
- 前台通过 `parentId === currentMenu.id` 筛选分类；
- **优点**：不新增字段，满足成员4 页面归属需求；
- **缺点**：破坏 `parentId` 原本的"分类父级"语义；
- **前提**：后端必须**取消/调整** `news_category.parent_id → news_category.id` 自关联外键，否则无法写入 menu.id；
- **当前状态**：已定稿采用；数据写入被 schema 阻塞（DATA_CONFLICT），待后端修复后由成员3受控写入 parentId=11。

#### 方案 C：新增归属字段（**长期规范，非当前执行**）
- 新增 `owner_menu_id`（指向 menu.id）或 `channel_code`（所属频道）；
- `parentId` 继续表示分类父级，`owner_menu_id` / `channel_code` 表示归属；
- **优点**：语义最干净、长期可维护；
- **缺点**：需后端改表 + 接口。

### 15.5 最终决策（2026-06-02 定稿）

| 方案 | 状态 | 说明 |
|------|------|------|
| **方案 B** | **当前最终采用** | 复用 `news_category.parentId` 表示所属菜单 id（`menus.id`）；前台 `news_categories.filter(item => item.parentId === currentMenu.id)`；点击分类时 `/news/show-list?category_id=news_category.id` |
| **方案 A** | 不再作为当前执行方案 | 仅作为**后端未修复前的临时降级**：`/news` 固定读取全部 `/news-categories`，不按 parentId 筛选 |
